## 1. 模块概述

### 1.1 模块定位

AI 分析引擎模块是平台的**核心技术底座**，为三个核心助手（价值评估、一致性检查、问题归因）提供统一的 AI 能力支撑。它包含四个子引擎：**RAG 管道**（文档检索增强生成）、**LangGraph 工作流引擎**（多步骤分析编排）、**规则引擎**（确定性冲突判定）和**连接器框架**（外部系统数据接入）。所有 LLM 调用均通过本模块的模型治理层记录和管控。

### 1.2 解决的业务问题

- **信息检索**：将散落在多份文档中的信息通过混合检索（语义 + 关键词）精准定位
- **分析编排**：多步骤分析任务（输入校验 → 检索 → 规则判定 → LLM 推理 → 证据组装 → 人工确认）的有状态编排
- **成本控制**：确定性冲突由规则引擎判定，减少 LLM 调用；单任务 token 上限控制
- **证据可靠**：每条结论绑定引用位置，区分"事实"和"推断"，低置信度明确标注
- **可复现性**：记录大模型版本、提示词版本、温度参数，保证同输入可复现

### 1.3 在整体架构中的位置

本模块位于 **LangGraph AI 分析层**和**数据与集成层**：

```
应用服务层（三个助手 Service）
        │
        ▼
┌────────────────────────────────────┐
│     LangGraph AI 分析层（本模块）    │
│  ┌──────────────────────────────┐  │
│  │   LangGraph Workflow Engine  │  │
│  │   (通用状态图 + 三工作流)     │  │
│  └─────────────┬────────────────┘  │
│                ▼                    │
│  ┌──────────────────────────────┐  │
│  │      RAG Pipeline            │  │
│  │  解析 → 分割 → 嵌入 → 检索   │  │
│  └─────────────┬────────────────┘  │
│                ▼                    │
│  ┌──────────────────────────────┐  │
│  │  规则引擎 + 证据链 + 模型治理 │  │
│  └──────────────────────────────┘  │
```

## 4. 子引擎一：RAG 管道

### 4.1 架构概述

RAG 管道分为**离线索引管道**（文档 → 解析 → 分割 → 嵌入 → 向量库）和**在线检索管道**（查询 → 混合检索 → 重排序 → 上下文组装）。

```
离线索引管道：  文档 → Parser → Splitter → Embedder → Vector Store
在线检索管道：  Query → Hybrid Retriever → Reranker → Context Assembly
```

### 4.2 文档解析器

| 解析器 | 支持格式 | 关键能力 |
| --- | --- | --- |
| `MarkdownParser` | `.md` | 保留标题层级作为 section_path |
| `OpenAPIParser` | OpenAPI 2/3, Swagger JSON/YAML | 按 path + method + schema 结构化提取 |
| `ExcelParser` | `.xlsx`, `.csv` | 保留表头行作为字段上下文 |
| `DocxParser` | `.docx` | 段落 + 表格分别提取 |
| `PdfParser` | `.pdf` | PyMuPDF 文本提取 |
| `TextParser`（基类） | `.txt`, 纯文本 | 无条件解析 |

所有解析器输出统一的 `ParsedDocument` 结构：
```python
@dataclass
class ParsedDocument:
    content: str                 # 纯文本内容
    metadata: dict               # {title, author, version, source_system, ...}
    sections: list[dict]         # [{heading, level, content, page}]
```

### 4.3 文本分割

- **算法**：`RecursiveCharacterTextSplitter`（优先按段落 → 句子 → 词语边界分割）
- **参数**：`chunk_size=1024` tokens, `chunk_overlap=128` tokens
- **元数据注入**：每个 chunk 携带 `{project_id, doc_type, doc_id, version, section_path, access_level, tenant_id}`
- **租户标识**写入 metadata，检索时强制过滤

### 4.4 脱敏处理

在分块后、嵌入前执行。敏感信息匹配规则：

| 类型 | 正则 | 替换 |
| --- | --- | --- |
| 手机号 | `1[3-9]\d{9}` | `1*********` |
| 邮箱 | `[a-zA-Z0-9._%+-]+@...` | `***@***.***` |
| 身份证号 | `\d{17}[\dXx]` | `******************` |
| API Key/Token | `(sk\|api[_-]?key\|token)[=:]\s*[\w-]+` | `{name}=***` |

### 4.5 混合检索

```python
class HybridRetriever:
    """Dense（向量余弦相似度）+ Sparse（BM25 关键词）混合检索"""

    def __init__(self, alpha: float = 0.7):
        self.alpha = alpha  # 语义权重

    async def search(
        self, query: str, top_k: int = 20, filters: dict | None = None
    ) -> list[dict]:
        # Dense: 向量检索 (top_k * 2)
        dense_results = await vector_store.search(query, k=top_k * 2, filter=filters)
        # Sparse: BM25 关键词检索 (top_k * 2)
        sparse_results = bm25_index.search(query, k=top_k * 2)
        # Reciprocal Rank Fusion 融合排序
        merged = rrf_fusion(dense_results, sparse_results, alpha=self.alpha)
        # Cross-encoder 重排序
        reranked = cross_encoder.rerank(query, merged[:top_k * 2])
        return reranked[:top_k]
```

**检索模式**：

| 模式 | 过滤条件 | 适用场景 |
| --- | --- | --- |
| 按需求ID精确检索 | `requirement_id = X` | 价值评估、交付物检查 |
| 按维度跨文档检索 | `doc_type IN (...)` | 一致性检查（跨 PRD/接口/埋点） |
| 按时间窗检索 | `timestamp BETWEEN A AND B` | 问题归因 |
| 混合过滤 | `project_id + doc_type + time_range + tenant_id` | 通用 |

### 4.6 Prompt 模板管理

所有 Prompt 模板保存在 `rag/prompts/` 目录，纳入 Git 版本控制。分析任务记录 `prompt_version`（Git commit hash）。

**模板结构**：
```
System: 角色定义 + 输出格式约束 + 评分锚点/归因类别定义
Context: [检索到的文档 chunk，带引用标记 [doc_id:section]]
Task: 具体分析任务
Instruction: 区分"引用材料的事实"和"基于锚点的推断"
Output: JSON Schema 约束的结构化输出
```

### 5.2 通用任务状态图节点

| 节点 | 对应 PRD 状态 | 职责 | 输入 | 输出 |
| --- | --- | --- | --- | --- |
| `validate_input` | validating | 校验必填项、数值范围、数据源可用性 | input_snapshot | valid/invalid 路由 |
| `lock_snapshot` | analyzing | 锁定输入材料快照，写入 MinIO | task_id | snapshot_id |
| `retrieve_docs` | analyzing | RAG 混合检索 | query + filters | retrieved_docs + metadata |
| `run_rules` | analyzing | 规则引擎执行确定性判定 | rule_items | rule_results |
| `llm_analyze` | analyzing | LLM 推理（评分/比对/归因） | retrieved_docs + rule_results | llm_results |
| `link_evidence` | analyzing | 证据链组装、区分事实/推断/缺失 | llm_results | evidence_chain |
| `calc_confidence` | analyzing | 置信度计算（高/中/低） | evidence_chain | confidence_summary |

### 5.4 条件路由逻辑

```python
def route_after_retrieval(state: AnalysisState) -> str:
    """确定性项走规则引擎，语义项走 LLM。降低成本的关键优化点。"""
    check_items = state.get("check_items", [])
    deterministic = [i for i in check_items if is_deterministic(i)]
    semantic = [i for i in check_items if not is_deterministic(i)]

    # 如：字段类型匹配 (string vs integer) → 确定性可判定
    # 如：两个文档的字段定义是否语义等价 → 需要 LLM
    if deterministic:
        state["rule_items"] = deterministic
        state["llm_items"] = semantic
        return "has_rule_items"
    return "llm_only"
```

### 5.5 人工确认中断机制

```python
# human_review 节点：
# 1. 更新 task.status = 'pending_review'
# 2. 持久化当前状态（checkpoint 自动保存）
# 3. 通过 WebSocket 推送通知用户

# 外部 API 调用恢复：
# POST /api/v1/tasks/{task_id}/assessment/confirm

```

### 5.6 检查点与恢复

- 使用 PostgreSQL 作为 LangGraph checkpointer（`PostgresSaver`）
- 每个任务以 `task_id` 作为 `thread_id`
- 失败任务可从最近的 checkpoint 恢复，避免重复执行已完成节点
- 同一任务不可重复提交（Redis 分布式锁 `task:lock:{task_id}`）

## 6. 子引擎三：规则引擎

### 6.1 设计原则

PRD 6.3.2 明确要求：**规则可检测的确定性冲突优先由规则直接判定，降低 LLM 调用成本和延迟。**

### 6.2 规则 DSL

```
规则 DSL 语法（EBNF）：

rule         := "MATCH" source "WITH" target condition+ "RETURN" result
source       := path ("WHERE" filter)?
target       := path ("WHERE" filter)?
path         := identifier ("." identifier | "[*]" | "[" index "]")*
condition    := "WHERE" comparison ("AND" comparison)*
comparison   := path operator value
operator     := "=" | "!=" | ">" | "<" | "IN" | "CONTAINS"
result       := "CONFLICT" | "MISSING"
```

**示例规则**（字段类型一致性检查）：
```
MATCH prd.fields[*].type
WITH api.schema.properties[*].type
WHERE name = name
RETURN CONFLICT IF type != type
```

### 6.3 五维检查规则

| 维度 | 规则文件 | 典型判定项 |
| --- | --- | --- |
| `field` | `field_rules.py` | 名称、类型、长度、必填、枚举值、默认值、脱敏规则 |
| `flow` | `flow_rules.py` | 前置条件、步骤、状态节点、分支、终止条件 |
| `permission` | `permission_rules.py` | 角色、数据范围、操作权限、审批规则 |
| `exception` | `exception_rules.py` | 错误条件、错误提示、重试、降级、补偿 |
| `acceptance` | `acceptance_rules.py` | 指标、口径、边界值、预期结果 |

### 6.4 规则执行

```python
class RuleEngine:
    async def load_rules(self, db, project_id) -> None:
        """加载项目启用规则。项目规则优先级高于通用规则。"""

    def execute(self, documents: dict[str, ParsedDocument]) -> list[dict]:
        """对所有文档执行所有适用规则。
        Returns: [{rule_id, dimension, title, level, confidence: "high",
                   involved_docs: [{doc_id, citation, excerpt}],
                   comparison: str}]"""
```

- 规则引擎判定结果置信度标记为 `high`（确定性高）
- 规则冲突时暂停受影响规则，通知管理员处理（PRD 异常处理）

| `model_name` | 如 `claude-opus-4-8` |
| `model_version` | API 返回的版本标识 |
| `prompt_template_version` | Git commit hash |
| `temperature` | 关键结论 ≤ 0.3 |
| `max_tokens` | 最大输出 token |
| `prompt_tokens` / `completion_tokens` / `total_tokens` | Token 用量 |
| `latency_ms` | 调用延迟 |
| `request_id` | API request_id |
| `is_cached` | 是否命中缓存 |

### 8.2 治理规则

- 同一分析任务所有 LLM 节点使用同一模型版本
- 模型升级后新任务默认新版本，历史任务可指定原版本复现
- 单任务 token 上限：评估 32K / 检查 64K / 归因 128K
- 按任务类型统计调用量、延迟和成本
- 同输入 + 同模型 → 结果差异超阈值时触发一致性告警

## 9. 性能优化策略

| 策略 | 实现 | 效果 |
| --- | --- | --- |
| 规则预过滤 | 条件路由：确定性项不调用 LLM | 减少 30%-50% LLM 调用 |
| Map-Reduce 并行 | LangGraph Send API 并行处理维度 | 五维评分并行，总时间 ≈ max(单维度) |
| LLM 缓存 | LangChain Redis Cache（TTL 1h） | 相同 Prompt 命中缓存 |
| 检索结果缓存 | Redis 缓存查询 → 文档 ID 映射（TTL 5min） | 重复查询加速 |
| Token 预算 | TokenBudget 类控制单任务消耗 | 避免成本失控 |
| 超时控制 | LLM 调用 120s / 向量检索 10s / 文档解析 60s | 异常快速失败 |
