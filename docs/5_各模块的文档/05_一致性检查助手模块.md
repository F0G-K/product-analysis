## 1. 模块概述

### 1.1 模块定位

交付物一致性检查助手是平台的**第二个核心助手**，在产品研发提测前，对 PRD、原型说明、接口文档、埋点方案和测试用例进行跨文档比对，识别**字段、流程、权限、异常状态和验收条件**五个维度的一致性冲突和遗漏。采用**规则引擎 + LLM 语义比对**双层架构，确定性冲突由规则直接判定，语义差异由大模型识别。

### 1.2 解决的业务问题

- 各角色文档间的字段定义、状态流转、权限规则互相矛盾
- 问题在联调、测试甚至上线后才暴露，返工成本高
- 没有统一的检查标准，每次靠人工逐文档比对，效率低且遗漏多
- 问题整改缺乏追踪闭环

### 1.3 核心流程概览

```
创建基线（关联交付物） → 创建检查任务 → 五维并行检索
    → 规则引擎前置过滤（确定性冲突）→ LLM 语义比对（语义差异）
    → 问题分级（阻断/严重/一般/提示）→ 人工处置 → 复检 → 关闭
```

### 2.2 检查维度与典型检查项

| 维度 | 典型检查项 | 示例 |
| --- | --- | --- |
| **字段 (field)** | 名称、类型、长度、必填、枚举、默认值、脱敏规则 | PRD 要求手机号必填，接口定义为可选 |
| **流程 (flow)** | 前置条件、步骤、状态、分支、终止条件 | 原型存在撤回入口，PRD 未定义撤回状态 |
| **权限 (permission)** | 角色、数据范围、操作权限、审批规则 | 接口允许普通成员删除，PRD 仅允许管理员 |
| **异常状态 (exception)** | 错误条件、提示、重试、降级、补偿 | 测试用例未覆盖支付超时后的补偿 |
| **验收条件 (acceptance)** | 指标、口径、边界、预期结果 | PRD 定义成功率，埋点缺少失败事件 |

### 2.3 问题分级

| 级别 | 判定标准 | 处理要求 |
| --- | --- | --- |
| **阻断 (blocker)** | 可能造成核心流程不可用、越权、数据错误或无法验收 | 提测前必须关闭或由负责人书面豁免 |
| **严重 (critical)** | 影响重要分支、主要指标或大范围用户体验 | 应在当前版本关闭 |
| **一般 (general)** | 影响非核心场景，存在明确替代方案 | 可排期修复，需记录计划 |
| **提示 (info)** | 表述不清、轻微缺失或规范建议 | 由责任人判断是否处理 |

## 6. 业务逻辑与服务层

### 6.1 ConsistencyService 核心方法

| 方法 | 职责 |
| --- | --- |
| `create_baseline(requirement_id, deliverables, scope)` | 创基线 → 锁定交付物快照 → 写入 MinIO |
| `create_check_task(baseline_id, rule_ids)` | 载入规则 → 创建 Task + CheckTask → 投递 Celery |
| `get_check_detail(task_id)` | 返回问题清单 + 统计（blocker/critical/general/info 数量） |
| `assign_issue(issue_id, assignee, operation)` | 流转问题状态 → 记录处置 → 阻断豁免校验 |
| `recheck_issue(issue_id, baseline_id)` | 仅对已修正问题 → 执行关联规则 → passed/failed |
| `get_issues(task_id, filters)` | 按维度/级别/状态/责任人筛选 |

### 6.2 核心业务流程

#### 6.2.1 检查执行流程

```
1. 基线准备：指定需求 + 关联五类交付物（至少 PRD + 1 类其他）
2. 基线创建：系统锁定交付物快照版本 → 生成不可变基线编号 BL-{project}-{seq}
3. 检查任务创建：选择检查范围（全量/增量/指定规则）→ 投递 Celery
4. LangGraph 工作流执行：
   a. 输入校验：交付物材料可访问、至少 PRD+1 类
   b. 快照锁定：基线交付物版本写入 MinIO
   c. 五维并行检索：
      - 字段维度：检索所有交付物中字段定义
      - 流程维度：检索状态机定义
      - 权限维度：检索角色和权限规则
      - 异常状态维度：检索错误处理和异常分支
      - 验收条件维度：检索指标和边界
   d. 每维度内：
      - 确定性冲突 → 规则引擎直接判定（字段类型不匹配、枚举值缺失等）
      - 语义差异 → LLM 比对（两个文档对同一概念的不同表述）
   e. 合并问题清单 → 分级 → 构建双向引用定位
5. 结果：问题详情含涉及交付物 + 精确引用位置 + 对照说明
```

#### 6.2.2 规则引擎 vs LLM 分工

```
规则引擎判定（确定性高，置信度=high）：
  - 字段类型不匹配（string vs integer）
  - 必填 vs 可选冲突
  - 枚举值集合不一致
  - 状态节点缺失/多余
  - 角色权限直接冲突

LLM 语义比对（确定性低，需语义理解）：
  - 同一概念的不同表述（如 "用户状态" vs "账号状态"）
  - 流程步骤描述的语义等价
  - 异常处理策略的意图比对
  - 验收口径的语义一致性
```

#### 6.2.3 问题处置流程

```
pending (系统生成)
    │
    ▼
任务负责人确认有效 → 分配责任人
    │
    ▼
acknowledged (已认领)
    │
    ▼
in_progress (责任人在外部系统修正交付物)
    │
    ▼
pending_recheck (提交新材料版本)
    │
    ▼
recheck:
    ├── passed → closed
    ├── failed → back to in_progress
    │
    ├── waived (豁免) → waived
    │   阻断级豁免需两方确认 (waiver_approvals ≥ 2)
    │
    └── false_positive (误报) → false_positive
        需说明原因，反馈用于规则优化
```

## 7. LangGraph 工作流设计

### 7.1 工作流图

```
[START] → validate_input → lock_snapshot → retrieve_docs (5维并行检索)
    │
    ▼
Map: 五维并行
    ├── check_field_docs        → route → run_rules (field)      → llm_compare (field)
    ├── check_flow_docs         → route → run_rules (flow)       → llm_compare (flow)
    ├── check_permission_docs   → route → run_rules (permission) → llm_compare (permission)
    ├── check_exception_docs    → route → run_rules (exception)  → llm_compare (exception)
    └── check_acceptance_docs   → route → run_rules (acceptance) → llm_compare (acceptance)
    │
    ▼
Reduce: 合并冲突清单
    ├── 按维度分组
    ├── 去重合并
    ├── 级别判定（阻断/严重/一般/提示）
    └── 双向引用定位
    │
    ▼
link_evidence → calc_confidence → finalize → [END]
```

### 7.2 关键优化：规则引擎前置路由

```python
def route_after_retrieval(state, dimension):
    """每维度的检查项分为确定性和语义性两类。"""
    check_items = state[f"{dimension}_items"]
    deterministic = [i for i in check_items if is_deterministic(i)]
    semantic = [i for i in check_items if not is_deterministic(i)]

    if deterministic:
        # 规则引擎先跑，结果置信度=high
        state[f"{dimension}_rule_results"] = rule_engine.execute(deterministic)
    if semantic:
        # LLM 再跑语义比对
        state[f"{dimension}_llm_items"] = semantic
    return "llm_compare" if semantic else "done"
```

### 7.3 复检子流程

复检是独立的轻量工作流：仅针对被修正的问题，执行触发该问题的规则子集和新材料比对。不复用完整五维检查工作流。

```
复检触发 (POST /check-issues/{id}/recheck)
    │
    ▼
锁定新材料版本 → 执行该问题关联的规则 → 通过/不通过
    │
    ├── passed → issue.status = 'closed'
    └── failed → issue.status = 'in_progress'
```

## 9. 异常处理与边界条件

| 场景 | 处理方式 |
| --- | --- |
| 仅 PRD 无其他交付物 | 允许执行单文档完整性检查，结果标注"不构成完整一致性结论" |
| 多文档冲突且无主版本 | 阻止正式检查，要求指定主版本 |
| 规则互相冲突 | 暂停受影响规则，通知管理员处理，不静默覆盖 |
| 检查超时（> 10min） | 保留已完成阶段的检查结果，支持缩小范围重试 |
| 分析期间材料变更 | 当前任务继续使用快照，完成后提示创建新基线 |
| 交付物文件解析失败 | 标记失败文件和原因，用户替换后重试 |
| 增量检查无上一基线 | 降级为全量检查 |
| 无足够交付物执行指定维度 | 该维度跳过并在报告中注明 |

### 10.3 PRD 验收标准覆盖

- 用户可关联五类交付物并查看来源、版本和同步状态
- 系统能按五个维度输出问题，每个问题含双向或多向引用
- 增量检查仅覆盖变更及受影响范围
- 问题状态流转符合权限和前置条件，关闭后保留完整记录
- 未解决阻断项存在时报告明确显示"不可直接通过"
- 同一输入快照和规则版本重复执行时关键结论保持一致
