# 概要设计 总纲

本文档约 9000 字，基于 [PRD V1.2](../1_prd/产品管理智能助手平台_PRD.md) 和 [原型图](../2_原型图/README.md) 编写。

## 1. 设计目标与原则

### 1.1 设计目标

平台以**大语言模型（LLM）为核心分析引擎**，将分散在 PRD、原型、接口文档、埋点方案、测试用例、日志、监控、工单、代码变更中的非结构化信息，通过 RAG（检索增强生成）技术转化为可解释的评分、问题清单和归因建议。

核心目标：
- 统一分析入口：三个助手（价值评估、一致性检查、问题归因）共享同一套 RAG 管道。
- 证据可追溯：每条结论绑定引用位置，区分事实与推断，支持人工确认。
- 规则 + 大模型协同：确定性检查由规则引擎处理，语义理解由大模型完成，兼顾效率和深度。
- 异步可恢复：分析任务异步执行，失败可重试，历史结论可复现。

### 1.2 设计原则

| 原则 | 说明 | 对应 PRD 章节 |
| --- | --- | --- |
| 检索增强生成（RAG）优先 | 所有大模型调用基于检索到的上下文，杜绝凭空生成 | 5.1, 9.5 |
| 规则优先于模型 | 确定性冲突由规则引擎判定后再送大模型做语义比对 | 6.3.2 |
| 快照不可变 | 分析任务锁定输入快照，保证结论可复现 | 5.1, 6.5 |
| 人工决策节点 | 评分确认、问题豁免、归因结论必须经人工确认 | 6.2.5, 6.3.5, 6.4.6 |
| 模型治理 | 记录模型版本、提示词版本、温度参数，同一任务同一模型版本 | 9.5 |
| 租户隔离 | 数据、检索、缓存、分析结果均带租户标识 | 9.3 |

### 2.2 框架选型理由

#### 2.2.1 LangGraph — 核心编排框架

**选定：LangGraph**（Python）

PRD 定义的三个助手任务流程均具有"多步骤、有条件分支、需要人工确认节点"的特征。LangGraph 是 LangChain 团队推出的有状态图工作流框架，适合此类场景：

| 需求 | LangGraph 能力 |
| --- | --- |
| 多步骤分析流程（输入校验→检索→评分/比对/归因→结果结构化） | StateGraph 定义节点和边，管理跨步骤状态 |
| 条件分支（规则可判断项跳过 LLM、阻断问题需额外审批） | conditional_edges 实现条件路由 |
| 人工确认节点（评分确认、问题豁免、归因确认） | interrupt 机制在指定节点暂停，等待人工输入后恢复 |
| 失败重试与断点续跑 | checkpoint 持久化图状态，支持从失败节点恢复 |
| 模型版本绑定 | 图状态中记录模型版本，同任务所有 LLM 节点使用同一版本 |
| 并行文档检索 | Send API 实现 Map-Reduce 模式的并行检索 |

#### 2.2.2 与 PRD 的映射

LangGraph StateGraph 的节点映射到 PRD 定义的任务状态机：

```
PRD 任务状态          LangGraph 节点
─────────────        ──────────────
草稿       ────────►  input_validation    (输入完整性校验)
待校验     ────────►  snapshot_lock       (锁定输入快照)
分析中     ────────►  retrieval           (RAG 检索)
                    ►  rule_check          (规则引擎判定)
                    ►  llm_analyze        (大模型分析)
                    ►  evidence_link      (证据链组装)
                    ►  confidence_calc    (置信度计算)
待确认     ────────►  human_review        (人工确认节点，中断等待)
已完成     ────────►  result_finalize     (结果持久化)
失败       ────────►  error_handler       (错误处理)
```

## 4. RAG 分析引擎设计

### 4.1 为什么用 RAG

PRD 定义的三个助手本质上都是"基于多源文档的分析推理"：

- **价值评估**：检索需求描述 → 比对评分锚点 → 生成五维评分
- **一致性检查**：检索 PRD/接口/原型/埋点/测试用例 → 跨文档语义比对 → 发现冲突
- **问题归因**：检索日志/监控/工单/代码变更/需求文档 → 时间线聚合 → 归因推理

三个场景都不适合微调模型（文档持续变化、需要精确引用位置、结论必须绑定证据），RAG 是最合适的架构。

**关键参数**（基于 PRD 非功能需求）：
- `chunk_size = 1024 tokens`，`chunk_overlap = 128 tokens`，保证语义连续性
- 脱敏在分块后、嵌入前执行，避免脱敏影响语义理解精度
- 每条 chunk 携带 metadata：`{project_id, doc_type, doc_id, version, section_path, access_level}`
- 租户标识写入 metadata，检索时强制过滤

#### 4.3.2 检索策略

```
Hybrid Search = Dense (向量余弦相似度) × α + Sparse (BM25 关键词) × (1-α)

默认 α = 0.7（偏重语义），关键词匹配权重可配置。
```

| 检索模式 | 适用场景 |
| --- | --- |
| 按需求ID精确检索 | 价值评估：检索该需求关联的全部文档 |
| 按维度跨文档检索 | 一致性检查：检索"字段定义"跨 PRD/接口/埋点 |
| 按时间窗检索 | 问题归因：检索异常时间窗前后的所有事件 |
| 混合过滤 | 项目ID + 文档类型 + 时间范围 + 租户 |

检索结果经 cross-encoder (BGE-Reranker) 重排序，Top-K 默认 = 20，单次调用上限由 token 预算控制。

### 4.4 生成与证据链

**Prompt 模板结构**（每个助手独立维护，纳入版本管理）：

```
System: 角色定义 + 输出格式约束 + 评分锚点/归因类别定义
Context: [检索到的文档 chunk，带引用标记 [doc_id:section]]
Task: 具体分析任务（评分/比对/归因）
Instruction: 区分"引用材料的事实"和"基于锚点的推断"
Output: JSON Schema 约束的结构化输出
```

**证据链组装规则**（PRD 6.2.4、6.3.4、6.4.4）：
- 每个结论必须绑定 `引用位置`（文档ID + 章节/字段路径）
- 无法定位引用时 → 降低置信度 → 标记为推断
- 输出区分三类标签：
  - `证据`：直接引自输入材料
  - `推断`：大模型基于锚点/规则推理
  - `缺失`：当前材料无法覆盖，需补充

```python
    project_id: str
    tenant_id: str
    task_type: Literal["assessment", "consistency_check", "attribution"]
    status: str                    # 对应 PRD 任务状态
    input_snapshot: dict           # 锁定输入快照
    retrieved_docs: list           # 检索结果
    rule_results: list             # 规则引擎结果
    llm_results: dict              # 大模型分析结果
    evidence_chain: list           # 证据链
    model_version: str             # 模型版本（固定）
    prompt_version: str            # 提示词版本
    errors: list

# 通用图结构
workflow = StateGraph(AnalysisState)

# 节点
workflow.add_node("validate_input", validate_input_node)
workflow.add_node("lock_snapshot", lock_snapshot_node)
workflow.add_node("retrieve_docs", retrieve_docs_node)      # RAG 检索
workflow.add_node("run_rules", run_rules_node)               # 规则引擎
workflow.add_node("llm_analyze", llm_analyze_node)           # LLM 推理
workflow.add_node("link_evidence", link_evidence_node)       # 证据组装
workflow.add_node("calc_confidence", calc_confidence_node)   # 置信度
workflow.add_node("human_review", human_review_node)         # 人工确认(中断)
workflow.add_node("finalize", finalize_node)
workflow.add_node("handle_error", handle_error_node)

# 边
workflow.add_edge(START, "validate_input")
workflow.add_conditional_edges("validate_input", route_after_validate, {
    "valid": "lock_snapshot",
    "invalid": "handle_error"
})
workflow.add_edge("lock_snapshot", "retrieve_docs")
workflow.add_conditional_edges("retrieve_docs", route_after_retrieval, {
    "has_rule_items": "run_rules",    # 规则可判定项优先
    "llm_only": "llm_analyze"
})
workflow.add_edge("run_rules", "llm_analyze")
workflow.add_edge("llm_analyze", "link_evidence")
workflow.add_edge("link_evidence", "calc_confidence")
workflow.add_edge("calc_confidence", "human_review")
workflow.add_conditional_edges("human_review", route_after_review, {
    "confirmed": "finalize",
    "revised": "llm_analyze",         # 修正后重新分析
    "rejected": "handle_error"
})
workflow.add_edge("finalize", END)
workflow.add_edge("handle_error", END)

# 持久化检查点 (支持断点续跑和失败重试)
app = workflow.compile(checkpointer=MemorySaver())
```

```python
# Map-Reduce 并行评分
def map_dimension_scoring(state):
    """使用 Send API 并行评估五个维度"""
    dimensions = [
        {"name": "用户覆盖", "weight": 0.20, "direction": "正向"},
        {"name": "业务价值", "weight": 0.30, "direction": "正向"},
        {"name": "战略匹配度", "weight": 0.20, "direction": "正向"},
        {"name": "实现成本", "weight": 0.15, "direction": "反向"},
        {"name": "风险", "weight": 0.15, "direction": "反向"},
    ]
    return [Send("score_dimension", {"dim": d, "req": state["input_snapshot"]})
            for d in dimensions]

def reduce_scores(scores):
    """汇总五维评分，计算总分和优先级"""
    total = sum(s["raw_score"] / 5 * 100 if s["正向"]
                else (6 - s["raw_score"]) / 5 * 100
                for s in scores)  # ... 加权计算
    priority = "P0" if total >= 80 else "P1" if total >= 65 else "P2" if total >= 50 else "P3"
    return {"total_score": total, "priority": priority, "dimensions": scores}
```

核心优化：规则引擎前置过滤。PRD 6.3.2 明确要求"规则可检测的确定性冲突优先由规则直接判定，降低大模型调用成本和延迟"。

```python
def route_after_retrieval(state):
    """确定性和语义性分离路由"""
    deterministic_items = []
    semantic_items = []

    for check_item in state["check_items"]:
        # 如：字段类型匹配 (string vs integer) → 确定性可判定
        if is_deterministic(check_item):
            deterministic_items.append(check_item)
        else:
            # 如：两个文档的字段定义是否语义等价 → 需要 LLM
            semantic_items.append(check_item)

    state["rule_items"] = deterministic_items
    state["llm_items"] = semantic_items

    if deterministic_items:
        return "has_rule_items"
    return "llm_only"
```

## 8. 非功能需求实现方案

### 8.1 性能

| 指标 | PRD 要求 | 实现方案 |
| --- | --- | --- |
| 列表/详情页响应 | ≤ 2s (P95) | Redis 缓存热数据，PostgreSQL 索引优化，API 分页 |
| 单次价值评估 | ≤ 60s (P95) | LangGraph Map-Reduce 并行评分，检索结果缓存 |
| 单次一致性检查 | ≤ 10min (P95) | 规则引擎前置过滤 + 条件路由，减少 LLM 调用次数 |
| 单次归因分析 | ≤ 15min (P95) | 时间窗限制，事件采样，增量检索 |

### 8.2 安全

- **传输**：全链路 TLS 1.3
- **存储**：PostgreSQL TDE 加密，MinIO 服务端加密
- **认证**：JWT (access 30min) + Session Cookie (HttpOnly + Secure + SameSite=Lax)
- **凭据**：外部数据源凭据存入专用 Secret Manager，不写日志不写配置文件
- **脱敏**：手机号、身份证、邮箱、密钥在进入 RAG 管道前脱敏
- **租户隔离**：所有查询带 `tenant_id` 过滤器，数据库 Row-Level Security

## 9. 关键设计决策记录

| 决策 | 选项 | 选定 | 理由 |
| --- | --- | --- | --- |
| AI 编排框架 | LangGraph / LangChain Agent / 自研 | LangGraph | 有状态图、条件分支、中断机制、检查点持久化，匹配 PRD 任务状态机 |
| 向量数据库 | ChromaDB / Milvus / Pinecone / pgvector | ChromaDB(dev) / Milvus(prod) | 开发期零配置，生产期高并发、多租户过滤 |
| LLM 调用方式 | 直接 API / LangChain LLM Wrapper | LangChain Wrapper | 与 LangGraph 生态统一，Prompt Template 版本管理 |
| 规则引擎 | 自研 Python DSL / Drools / 表达式引擎 | 自研 Python DSL | 规则定义嵌入代码版本管理，无外部依赖 |
| 异步任务 | Celery / RQ / Dramatiq | Celery + Redis | 生态成熟，支持优先级队列、任务重试、结果存储 |
| 前端框架 | React / Vue / 静态 HTML | 原型阶段静态 HTML，生产阶段 React | 原型快速验证，生产阶段组件复用性要求高 |
