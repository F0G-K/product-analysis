## 1. 模块概述

### 1.1 模块定位

上线问题归因助手是平台的**第三个核心助手**，在上线异常发生后，聚合指定版本的**需求变更、代码变更、配置变更、测试记录、监控告警、日志和工单**等多源信息，按统一时间线排列，通过 LLM 推理判断问题最可能的来源（需求遗漏、设计缺陷、实现错误、配置变更、数据异常），每条结论附证据链和置信度。

### 1.2 解决的业务问题

- 线上异常信息分散在监控、日志、工单、代码仓库和项目文档中
- 问题定位依赖个人经验，难以快速判断来源属于哪类问题
- 缺少系统化的归因框架，复盘质量参差不齐
- 恢复时间长，缺少结构化的止损和改进建议

### 1.3 核心流程概览

```
创建归因任务（版本 + 时间窗 + 异常描述）
    → 自动拉取该版本的需求/代码/配置/测试记录
    → 聚合监控/日志/工单
    → 按事件类别并行检索 → 时间线聚合 → LLM 归因推理
    → 输出主要来源 + 促成因素 + 证据链 + 置信度
    → 人工确认（采纳/修正/异议）
```

### 2.2 五类归因定义

| 类别 | 定义 | 典型证据 |
| --- | --- | --- |
| **需求遗漏** | 需求未覆盖必要场景、边界或验收条件 | PRD 缺少异常分支，测试与实现均按原需求执行 |
| **设计缺陷** | 交互、流程、数据或技术方案设计不当 | 已定义场景，但方案在特定条件下必然失败 |
| **实现错误** | 代码实现与已确认需求或设计不一致 | 代码变更引入错误，回滚后指标恢复 |
| **配置变更** | 配置、开关、权限或发布参数不正确 | 配置变更时间与异常开始高度一致 |
| **数据异常** | 输入数据、存量数据、同步或计算结果异常 | 特定数据批次触发问题，代码和配置无变化 |

## 5. 数据库表与数据模型

> 完整字段定义见 [数据库设计文档 §3.6](../4_开发规范/数据库/数据库设计文档.md)。

### 5.1 涉及的数据表（5 张）

```
release_versions (N)
    │
    └── attribution_tasks (N, 继承 tasks)
            ├── timeline_events (N)
            ├── attribution_results (N, 1 primary + N contributing)
            └── attribution_confirmations (N)
```

### 5.2 核心表摘要

| 表名 | 关键字段 | 说明 |
| --- | --- | --- |
| `release_versions` | `id, project_id, version_number(UNIQUE), release_date, associated_requirements(JSONB), status(planned/released/rolled_back), release_notes` | 项目内版本号唯一 |
| `attribution_tasks` | `task_id(FK→tasks), release_version_id, anomaly_name, anomaly_window_start, anomaly_window_end, impact_scope, user_impact, current_handling_status, associated_alerts(JSONB)` | 继承 tasks |
| `timeline_events` | `attribution_task_id, event_source(7种), original_timestamp, project_timestamp, summary, source_url, related_object_type/id, event_data(JSONB), credibility(confirmed/uncertain)` | 按时间排序；不确定时间的进入"待定位证据" |
| `attribution_results` | `attribution_task_id, category(5种), is_primary, confidence(high/medium/low), supporting_evidence(JSONB), counter_evidence(JSONB), missing_evidence(JSONB), reasoning_chain, short_term_mitigation, long_term_improvement, suggested_owner_role` | 一条主归因 + 多条促成因素 |
| `attribution_confirmations` | `attribution_task_id, confirmed_by, operation(accept/revise/dispute), confirmed_category, revise_reason, dispute_explanation, dispute_resolved` | 异议处理 |

### 5.3 归因结论结构

每个归因结果的 evidence 字段（JSONB）采用三类证据体系：

```
supporting_evidence: [
    {"type": "fact",        # 事实（可直接验证）
     "source": "监控系统",
     "citation": "Prometheus alert #2871",
     "excerpt": "P99 latency spiked to 3.2s at 14:03:22"},
    {"type": "inference",   # 推断（模型基于证据的推理）
     "source": "LLM 推理",
     "excerpt": "配置变更时间与异常开始时间高度一致，间隔仅 45 秒"}
]
counter_evidence: [        # 反向证据（削弱该归因的证据）
    {"type": "fact",
     "source": "代码仓库",
     "excerpt": "同批次部署的其他服务未出现类似延迟"}
]
missing_evidence: [        # 缺失证据（待验证）
    "数据库慢查询日志在异常时间窗缺失",
    "未获取到配置变更的审批记录"
]
```

## 6. 业务逻辑与服务层

### 6.1 AttributionService 核心方法

| 方法 | 职责 |
| --- | --- |
| `create_attribution_task(version_id, anomaly_info)` | 校验版本存在 → 创建 Task + AttributionTask → 自动拉取关联材料 → 投递 Celery |
| `auto_fetch_materials(version_id, time_window)` | 从连接器拉取：需求变更/代码变更/配置变更/测试记录，失败时标记供人工补充 |
| `get_attribution_detail(task_id)` | 返回任务摘要 + 时间线 + 归因结果 + 证据链 |
| `confirm_attribution(task_id, confirmation)` | 确认/修正/异议；异议 unresolved 时标记 "结论有争议" |
| `add_manual_event(task_id, event)` | 手动添加时间线事件，标记 `credibility='uncertain'` 或 `'confirmed'` |

### 6.2 核心业务流程

#### 6.2.1 归因任务执行流程

```
1. POST /releases/{id}/attribute  { anomaly_name, time_window, impact_scope, alerts }
2. Service 校验：
   - 版本存在
   - 时间窗 ≤ 72h（超限建议拆分）
3. 创建任务 → 自动拉取关联材料：
   - 该版本关联的需求文档
   - 代码合并记录（Git diff + commit messages）
   - 配置变更记录（配置中心审计）
   - 测试记录（测试执行 + 缺陷关闭）
   - 时间窗内的监控告警
   - 时间窗内的异常日志
   - 时间窗内的用户工单
4. 投递 Celery → LangGraph 工作流
5. 返回 202 { task_id }
```

#### 6.2.2 时间线聚合

```
按项目时区（projects.timezone）统一排列所有事件：

时间线 = [
    需求变更事件（来自 PRD 仓库：需求修改时间、删除的场景）
    代码合并事件（来自 Git：PR/MR 合并时间、变更文件、commit message）
    配置变更事件（来自配置中心：变更时间、变更项、变更人）
    构建与发布事件（CI/CD：构建时间、发布完成时间、回滚时间）
    测试执行事件（测试用例执行记录、缺陷关闭时间）
    监控告警事件（Prometheus/Datadog：告警触发时间、指标突变值、持续时间）
    关键日志事件（ELK/Loki：异常堆栈、错误码突增、连接超时）
    用户工单事件（Jira/飞书：报障时间、问题描述、处置操作）
]

排序依据：project_timestamp（统一项目时区）
不确定时间 → 进入"待定位证据"（不参与强时序判断）
```

#### 6.2.3 LLM 归因推理

```
输入：
  - 异常描述 + 影响范围
  - 完整时间线（按时间排序）
  - 五类归因定义

LLM 输出（JSON Schema 约束）：
  {
    "primary_cause": {
      "category": "config_change",
      "confidence": "high",
      "supporting_evidence": [...],
      "counter_evidence": [...],
      "missing_evidence": [...],
      "reasoning_chain": "..."
    },
    "contributing_factors": [
      {"category": "design_flaw", "confidence": "medium", ...}
    ],
    "short_term_mitigation": "回滚配置项 X 至上一版本",
    "long_term_improvement": "为配置变更增加审批流程和灰度验证"
  }
```

## 7. LangGraph 工作流设计

### 7.1 工作流图

```
[START] → validate_input → lock_snapshot
    │
    ▼
Map: 按事件类别并行检索
    ├── retrieve_requirement_changes   (检索该版本的需求变更)
    ├── retrieve_code_changes          (检索 Git diff + PR)
    ├── retrieve_config_changes        (检索配置中心变更记录)
    ├── retrieve_test_records          (检索测试执行和缺陷)
    ├── retrieve_monitor_alerts        (检索监控告警, 时间窗)
    ├── retrieve_log_entries           (检索异常日志, 时间窗)
    └── retrieve_ticket_entries        (检索用户工单, 时间窗)
    │
    ▼
aggregate_timeline (时间线聚合)
    ├── 统一项目时区
    ├── 事件去噪（LLM 语义归纳：排除与异常无关的事件）
    ├── 排序
    └── 不确定时间事件 → 待定位证据
    │
    ▼
llm_attribute (LLM 归因推理)
    ├── 匹配五类归因
    ├── 提取支持证据 + 反向证据 + 缺失证据
    ├── 评估置信度 (高/中/低)
    └── 生成处置建议 (短期止损 + 长期改进)
    │
    ▼
link_evidence → calc_confidence_summary
    │
    ▼
human_review (中断等待确认)
    ├── confirmed → finalize → [END]
    ├── revised    → llm_attribute (重新归因) → ... → human_review
    └── disputed   → 标记 "结论有争议" → finalize → [END]
```

### 7.2 关键节点说明

| 节点 | 实现要点 |
| --- | --- |
| `retrieve_*` (7 个) | Send API 并行拉取不同数据源的事件 |
| `aggregate_timeline` | 时区转换使用 `projects.timezone`；LLM 语义归纳去噪 |
| `llm_attribute` | 单次 LLM 调用，输出完整的归因结构（JSON Schema） |
| `human_review` | 支持三种操作：accept/revise/dispute |

### 7.3 时区处理

- 所有事件的 `original_timestamp` 保留原始时区
- 统一转换为 `project_timestamp`（基于 `projects.timezone`）用于时间线排序
- 用户界面展示时使用项目时区

| 确认/修正/异议归因 | ✅ | ✅（任务负责人） | 任务负责人 | — |

### 8.2 数据安全

- 日志和监控数据可能含敏感信息，在进入 RAG 管道前脱敏
- 外部系统（监控/日志/工单）凭据加密存储
- 归因结论不作为个人绩效或责任处罚的唯一依据（PRD 6.4.6）

## 9. 异常处理与边界条件

| 场景 | 处理方式 |
| --- | --- |
| 时间窗 > 72h | 提交前提示拆分为多个时间窗 |
| 事件数 > 10 万 | 提交前提示缩小范围或采样分析 |
| 自动拉取失败（外部系统不可达） | 标记失败材料，用户可手动补充（标记来源） |
| 无法确定事件发生时间 | 进入"待定位证据"组，不参与强时序判断 |
| 证据不足无法区分多个类别 | 输出多个候选归因 + 待验证项，不强行给唯一结论 |
| LLM 无法确定置信度 | 默认标记为 'low' |
| 同输入重复执行结果不一致 | 记录 temperature 和模型版本；差异超阈值时触发一致性告警 |
| 分析期间外部数据更新 | 当前任务使用已锁定快照 |
| 归因任务超时（> 15min） | 保留过程状态，支持缩小时间窗重试 |

## 10. 测试要点

### 10.1 单元测试

| 测试类 | 关键覆盖 |
| --- | --- |
| `test_attribution_service` | 任务创建、材料拉取、确认/修正/异议 |
| `test_timeline_aggregation` | 时区转换、去噪、排序、不确定时间处理 |
| `test_attribution_inference` | 五类归因匹配、证据分类、置信度评估 |
| `test_evidence_classification` | 支持/反向/缺失证据的结构化输出 |

### 10.2 集成测试

| 场景 | 验证点 |
| --- | --- |
| 完整归因流程 | 创建版本 → 模拟异常数据 → 创建归因 → 查看时间线 → 确认归因 |
| 自动拉取失败 + 手动补充 | 连接器模拟失败 → 手动添加事件 → 正常归因 |
| 多归因同时输出 | 主要来源 + 促成因素 → 证据链完整 |
| 异议处理 | 提出异议 → 标记"结论有争议" |
| 时间线去噪 | 注入噪声事件 → LLM 正确排除 |
| 性能 | P95 归因 ≤ 15min (≤ 72h 时间窗 / 10 万事件) |

### 10.3 PRD 验收标准覆盖

- 系统可按版本和时间窗聚合六类输入材料（需求/代码/配置/测试/监控/日志/工单）
- 时间线中每条事件可查看来源、原始时间和关联对象
- 结果仅使用五类规定归因，并支持主要来源与促成因素
- 每个候选归因同时展示支持、反向和缺失证据
- 证据不足时不输出高置信度或唯一确定结论
- 用户可修正归因并保留原建议、修改理由及操作记录
