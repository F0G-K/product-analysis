## 1. 模块概述

### 1.1 模块定位

需求价值评估助手是平台的**第一个核心助手**，对需求池中的需求进行五维度量化评分（用户覆盖、业务价值、战略匹配度、实现成本、风险），输出带解释和证据引用的优先级建议。评估模型可配置，历史结论可复现，最终优先级由人工确认。

### 1.2 解决的业务问题

- 需求优先级不再靠拍脑袋或职位决定，有统一的五维量化标准
- 每项评分绑定证据引用，追溯评分依据
- 权重浮动 ±10% 后的敏感性分析判断结论是否稳定
- 历史评估结果和模型版本完整保留，可复现

### 1.3 核心流程概览

```
需求提交 → 选择评估模型 → 创建评估任务 → RAG 检索关联材料
    → 五维并行 LLM 评分 → 汇总计算总分 → 优先级建议 + 敏感性分析
    → 人工确认（采纳/修正/驳回）→ 结果持久化
```

### 2.2 评分模型

| 维度 | 默认权重 | 评分方向 | 换算公式 |
| --- | ---: | --- | --- |
| 用户覆盖 | 20% | 正向（越高越优） | `raw_score / 5 × 100` |
| 业务价值 | 30% | 正向 | `raw_score / 5 × 100` |
| 战略匹配度 | 20% | 正向 | `raw_score / 5 × 100` |
| 实现成本 | 15% | 反向（越低越优） | `(6 - raw_score) / 5 × 100` |
| 风险 | 15% | 反向 | `(6 - raw_score) / 5 × 100` |

**约束**：一级维度权重之和 = 100%，单维度权重 10%–40%。

### 2.3 优先级阈值

| 总分 | 建议优先级 | 处理建议 |
| ---: | --- | --- |
| 80–100 | P0 | 优先进入最近可用版本，必须完成成本与风险复核 |
| 65–79.9 | P1 | 纳入近期规划，明确依赖和资源 |
| 50–64.9 | P2 | 保留在需求池，补充证据后再排期 |
| 0–49.9 | P3 | 暂缓或关闭，记录原因 |

## 6. 业务逻辑与服务层

### 6.1 AssessmentService 核心方法

| 方法 | 职责 |
| --- | --- |
| `create_assessment(requirement_id, model_id, title)` | 校验需求状态=submitted → 校验模型状态=active → 创建通用Task → 创建AssessmentTask → 投递 Celery 任务 |
| `get_assessment_detail(task_id)` | 返回任务摘要 + 五维评分明细 + 敏感性 + 确认记录 |
| `confirm_assessment(task_id, confirmation)` | 校验确认权限 → 更新维度分数(若revise) → 标记needs_review(若P0/跨级) → 更新requirement.current_priority |
| `review_confirmation(confirmation_id, review)` | 复核人审批/驳回 |
| `get_assessment_history(requirement_id)` | 返回该需求所有历史评估 |

### 6.2 核心业务流程

#### 6.2.1 评估任务创建与执行

```
1. POST /requirements/{id}/assess  { model_id }
2. Service 校验：
   - requirement.status 必须为 'submitted'
   - model.status 必须为 'active'
   - 5 个维度 weight 之和 = 1.000
3. 创建 Task（task_type='assessment', status='draft'）
4. 创建 AssessmentTask（关联 requirement + model）
5. 投递 Celery: run_assessment_workflow.delay(task_id)
6. 返回 202 { task_id, status }

Celery Worker:
7. 加载 LangGraph checkpoint（thread_id=task_id）
8. 启动 assessment_workflow
9. 每节点更新 task.status → WebSocket 推送
```

#### 6.2.2 五维并行评分（LangGraph Map-Reduce）

```
lock_snapshot → retrieve_docs (获取需求描述 + 评分锚点 + 历史评估 + 战略文档)
    │
    ▼
Map 阶段（Send API 并行）:
    ├── 用户覆盖评分  ── LLM(检索到的用户覆盖材料 + 评分锚点)
    ├── 业务价值评分  ── LLM(检索到的业务价值材料 + 评分锚点)
    ├── 战略匹配度评分 ── LLM(检索到的战略材料 + 评分锚点)
    ├── 实现成本评分  ── LLM(检索到的成本估算 + 评分锚点) [反向维度]
    └── 风险评分      ── LLM(检索到的风险描述 + 评分锚点) [反向维度]
    │
    ▼
Reduce 阶段（汇总）:
    total = SUM(converted_score × weight)
    正向: converted_score = raw_score / 5 × 100
    反向: converted_score = (6 - raw_score) / 5 × 100
    priority = P0 if ≥80 else P1 if ≥65 else P2 if ≥50 else P3
    has_risk_flag = 合规红线 OR 关键依赖未解决 OR 风险维度 raw_score=5
```

#### 6.2.3 人工确认流程

```
1. 用户查看评估详情（含五维评分 + 证据 + 置信度）
2. 用户操作：
   a. accept  → 确认采纳
   b. revise → 修改维度分或优先级（必须填理由）
      - P0 确认或跨两级调整 → needs_review=true → 等待复核
   c. reject → 驳回（需说明原因）
3. 确认后：
   - 更新 task.status = 'completed'
   - 更新 requirement.current_total_score + current_priority
   - 写入 assessment_confirmations
   - 写入 audit_logs
   - 发送通知
```

## 7. LangGraph 工作流设计

### 7.1 工作流图

```
[START] → validate_input → lock_snapshot → retrieve_docs
    │
    ▼
map_dimension_scoring (Send API)
    ├── score_dimension: "用户覆盖" (LLM)
    ├── score_dimension: "业务价值"  (LLM)
    ├── score_dimension: "战略匹配度" (LLM)
    ├── score_dimension: "实现成本"   (LLM)
    └── score_dimension: "风险"       (LLM)
    │
    ▼
reduce_scores (汇总计算)
    │
    ▼
sensitivity_analysis (权重 ±10% × 5 组)
    │
    ▼
link_evidence (每维评分绑定证据)
    │
    ▼
calc_confidence (高/中/低)
    │
    ▼
human_review (中断等待确认)
    ├── confirmed → finalize → [END]
    ├── revised   → score_dimension (重新评分被修改维度) → reduce → ... → human_review
    └── rejected  → handle_error → [END]
```

### 7.2 关键节点说明

| 节点 | 实现要点 |
| --- | --- |
| `map_dimension_scoring` | 使用 `Send("score_dimension", {"dim": d})` 并行分发五个维度 |
| `score_dimension` | 每个维度独立调用 LLM，传入：评分锚点 + 需求描述 + 检索材料 |
| `reduce_scores` | 收集五个维度结果，加权计算总分，判定优先级，检测风险标记 |
| `sensitivity_analysis` | 对五个维度逐一 ±10%，检查优先级是否变化 |
| `human_review` | 使用 `interrupt` 机制暂停；用户确认后 `aupdate_state` + `astream` 恢复 |

### 7.3 LLM 调用参数

- 温度：0.3（关键结论需稳定）
- 输出格式：JSON Schema 约束
- 每维度独立 Prompt（含评分锚点 + 证据要求）
- 五维度并行调用（Map 阶段），总耗时 ≈ max(单个维度)

## 9. 异常处理与边界条件

| 场景 | 处理方式 |
| --- | --- |
| 需求信息不完整 | 阻止提交正式评估，生成缺失项清单（可保存草稿） |
| 评估模型未激活 | 返回 42204 MODEL_NOT_ACTIVE |
| 维度权重之和 ≠ 1.0 | 返回 42206 DIMENSION_WEIGHT_INVALID |
| 需求已存在进行中的评估 | 提示先完成或取消当前评估 |
| LLM 评分超时（> 60s） | 单维度超时不影响其他维度；超时维度标记为失败 |
| 证据不足（无法定位引用） | 标记 confidence='low'，标注 missing_evidence |
| 风险维度 raw_score=5 | has_risk_flag=true，不因总分高而自动 P0 |
| 人工修正跨两级调整 | needs_review=true，需另一审批人复核 |
| 分析期间需求被修改 | 使用已锁定快照继续分析，完成后提示创建新版本 |

### 10.1 单元测试

### 10.2 集成测试

| 场景 | 验证点 |
| --- | --- |
| 完整评估流程 | 创建需求 → 发起评估 → 等待完成 → 查看评分 → 确认 |
| 修正评分流程 | 修正分数 → 填理由 → P0 跨级需复核 |
| 评估历史 | 多次评估 → 历史列表按时间排序 |
| 模型版本升级 | 升级模型 → 新评估用新版本 → 历史评估不变化 |
| 性能 | P95 评估 ≤ 60s（PRD 9.1） |
| 可复现性 | 同一快照 + 同一模型版本 → 关键结论一致 |

### 10.3 PRD 验收标准覆盖

- 输入完整时可成功创建评估并获得五维评分
- 权重、反向维度和总分计算与规则一致（误差 ≤ 0.1）
- 每个系统评分可定位到证据或标记证据不足
- 模型更新后历史评估结果及版本保持不变
- 无审批权限用户不能确认或修改正式优先级
